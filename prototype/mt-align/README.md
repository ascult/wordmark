# 原型：用方法匹配词典义与实际语句（小模型只做挑选）

> **这是原型代码，不是生产实现。** 它验证的目标是：
> **提升释义质量——让标注出的是「该词在这句话里的那个义项」，而不是词典的第一个义项。**
>
> 两条腿：
> 1. **方法**：拿词典义去**实际那句译文**里定位——定位到的片段就是语境义（纯算法、零成本、可解释）；
> 2. **小模型**：方法定位不到时，让模型在**已有的词典义项里挑一个**（选择题，不生成新释义）。
>
> 验证完的结论落进生产代码，原型本身留在分支上作证据，不进 main。

## 为什么不是「让模型直接给释义」

模型生成释义的问题不是不准，而是**不可控也不可解释**：实测 41 个词里有 34% 的释义在实际译文里
找不到对应，且无法判断是模型错了还是译文漏了。而「在义项里挑一个」有两个硬好处：

- 输出永远是**真实词典义**，质量下限由词典保证；
- 输出只是一个序号，**任务变成选择题**，小模型可靠得多、延迟也低。

## 跑法

```bash
# 前置（本机 Apple M4 / 16GB）：本地 venv + mlx-lm + 小模型
cd .tmp-probe && uv venv --python 3.12 venv && uv pip install --python venv/bin/python mlx-lm
HF_HUB_DISABLE_XET=1 HF_HOME=$PWD/hf venv/bin/python -c \
  "from huggingface_hub import snapshot_download; snapshot_download('mlx-community/Qwen2.5-1.5B-Instruct-4bit')"

# 恢复多义项词典（现有生产词表每词只有一条压缩释义，没有义项可选）
node prototype/mt-align/build-senses.mjs

npm run proto:select      # 主张力：方法 vs 小模型「义项选择题」
npm run proto:match       # 词典义 → 译文 的匹配率（--expand 试候选扩展）
npm run proto:align       # 生成式对照（模型直出释义）
npm run proto:align:batch # 批量 vs 逐句延迟
```

`HF_HUB_DISABLE_XET=1` 不是可选项：Xet 后端在这台机器上被墙，不关掉任何缺失文件都会卡在 0 字节。

## 结论一：谷歌翻译不能当依赖，但「句级对齐」是白送的

| 事项 | 结果 |
| --- | --- |
| 可达性 | `client=gtx` 被拦（疑似自动查询）；`client=dict-chrome-ex` 可用 |
| 批量 | **POST 一次能翻整段**，每段都带回配对的源文片段 |
| 限流 | **十来个请求后来源 IP 被硬封**，退避重试 40 秒仍 429 |

一个页面几十上百句，靠它必然断。所以机翻只适合当「有则更好」的旁路，主路径要能自己出译文
（本地模型即可）。

## 结论二：**词典义 → 实际译文 的匹配方法可行**（这是用户设想的那一步）

实测 18 个「词表已收录」的词，用词典义去**实际译文**里定位：

| 匹配方式 | 定位率 | 与译文相容 | 成本 |
| --- | ---: | ---: | --- |
| 只用词典义（原样 + 最长公共子串） | 28% | **100%（构造保证）** | 0ms，纯算法 |
| 词典义 ∪ 小模型列举的候选说法 | **56%** | **100%（构造保证）** | 一次额外调用 |

「与译文相容 100%」是构造保证：标注片段本身就是译文里的子串——这正是「识别出原单词
翻译出的内容，再进行替换」。

失败的那一半是真问题，原因很具体：**机翻经常换用同义词，字面完全不重合**。
`ambitious` 词典义「有抱负的」，译文写的是「雄心勃勃」；`engine` 词典义「发动机」，译文写的是「动力」——
一个字都不重合，字符串方法无能为力。所以方法的天花板是「译文恰好复用了词典那些字」的情况。

`--expand` 把定位率从 28% 抬到 56% 的做法是：**让模型只负责列举候选说法**（同义词也算），
**用哪个仍由方法在译文里定位决定**。判断权留在方法手里，模型不参与决策。

## 结论三：小模型做「义项选择题」——1.5B 够用，0.5B 不行

`npm run proto:select`：8 个多义词，模型输出义项**序号**，对比三种挑选方式。

**Qwen2.5-1.5B-Instruct-4bit**：

| 挑选方式 | 有效作答 | 选中的义项确实出现在译文里 | 每条耗时 |
| --- | ---: | ---: | ---: |
| 方法（在译文里找义项） | 50% | **100%** | 0ms |
| 模型 A（不给译文） | **100%** | 38% | 989ms |
| 模型 B（给译文） | **100%** | 38% | 328ms |

**Qwen2.5-0.5B-Instruct-4bit**：0.5B **不可用**——连译文都产不出来
（把提示词「英文句子」原样抄回来），选择题有效作答仅 38–63%，与译文相容率 0%。

三条要点：

1. **选择题这个形式是成功的**：1.5B 的有效作答 100%，说明「挑义项」确实是它能稳定完成的任务
   （对比之下，多句批量那次它直接把输入抄了回来）。
2. **给不给译文完全不影响模型的选择**（A 与 B 一致率 100%）——译文对「挑选」没有增益。
   于是可以省掉这一步的机翻：**只有「方法」需要译文，模型挑选不需要**。
3. **模型会挑错，方法不会**。实例：`conservative` 在这句译文中是「过于保守」，
   方法精确选中「保守的」；模型选了「守旧的/传统的」。
   所以方法能定位时必须优先用方法。

「38% 与译文相容」也不该直接读成「模型准确率 38%」：这个代理指标要求选中义项的字面出现在译文里，
而译文本身会漏译改写（第 6 句把 `aptitude` 整段丢了），相容率因此被系统性低估。
它适合当**置信度信号**，不适合当准确率。

## 结论四：生成式路线不如挑选式

模型直出释义（不给义项）：覆盖率 100%，但只有 61–66% 的词其释义能在它自己那句译文里找到；
两段式（先译文再对齐）没有优势（63% vs 61%），却多一次调用和一个外部依赖。

对比之下，挑选式的输出永远是真实词典义，且天然与译文相容。**质量要靠「挑对义项」，
不是靠「让模型造句」。**

## 推荐的生产形态

1. **先补数据缺口：多义项词典。** 现在 `dict.zh.json` 每词只有一条压缩释义，
   根本没有义项可挑。上游 TypeWords 的 `trans[].cn` 本来就有，`build-senses.mjs` 已能恢复
   （2602 词，其中 **2413 个有 2 个以上义项**）。这是这一步的前提，也是收益最大、
   风险最低的一件事——**不依赖任何模型**。
2. **方法优先**：词表标注时，把「词典义在该句译文里定位到的片段」作为语境义。
   定位不到就退回首义项（现状），并在数据里记下「本句未定位到」。
3. **小模型补位**：仅当方法定位不到、且用户开启了 AI 时才调用，任务是
   **从义项里选一个**（输出序号），1.5B 足够，0.5B 不要用。**不需要把译文给它**（无增益）。
4. **机翻只服务于方法**，按句缓存；本地模型出译文即可，不必依赖谷歌。
5. **UI 上体现置信度**：定位到的义项是一等公民（可标 ✓）；模型挑的次之；都没把握就
   不标或标首义项。悬停给出整句译文，让人自己判断。

一句话：**你要的那条路（翻译→匹配回原词）走通了，但它只能覆盖一半；
另一半不是靠让模型造句，而是靠让模型在词典义里挑——两者都用「真实词典义」兜底。**

## 用大模型当 teacher：蒸馏「义项先验」

teacher 跑在本机的 OpenAI 兼容接口上（`http://127.0.0.1:8000`，`Qwen3.5-9B-MLX-4bit`）。
`openai.mjs` 是最小客户端（只用 Node 自带 fetch）；`distill.mjs` 是蒸馏流程。

### 必须先关掉「思考」，否则一切都是空的

**这是推理模型**：默认输出以 `Thinking Process:` 开头，把 `max_tokens` 全吃在思考里，
`content` 里根本拿不到答案（表现为「答了 0/12」，或请求超时）。实测六种设法：

| 设法 | 结果 |
| --- | --- |
| 原样 | ✗ `content` 全是 `Thinking Process:…` |
| 提示词加 `/no_think` | ✗ 无效 |
| **`chat_template_kwargs: {enable_thinking: false}`** | **✓ 干净返回 `4`，2427ms → 809ms** |
| 顶层 `enable_thinking: false` | ✗ 无效 |
| `reasoning_effort: "none"` | ✗ 无效 |
| `/no_think` + kwargs 组合 | ✓ 但没必要 |

关掉思考后，**批量输出也可靠**了：一次 6 条的原始输出是
`"1=1\n2=3\n3=1\n4=1\n5=1\n6=1"`，12/12 全部作答，约 0.75 秒/条。
（对比：本地 1.5B 做同样的批量时，直接把输入抄了回来。）

### 蒸馏什么、怎么验证

- **产物**：对每个多义词，统计 teacher 在真实句子里选中的义项次数，得到**按真实用法排序的义项表**
  （`distilled-senses.json`）。它是静态数据，可以直接打进扩展，**运行时不需要任何模型**。
  这正好补上现在的缺陷：扩展只能盲用上游词典的「第一个义项」，而那是词典编者的顺序，
  不是真实阅读中的使用顺序。
- **留一验证**（`distill.mjs` 内置）：每个词留出一条观察做测试，用其余观察排序，比较
  「按蒸馏排序取第一」与「永远取第一个义项」哪个更能命中 teacher 在被留出那句上的选择。
- **交叉校验**（`crosscheck.mjs`）：蒸馏的前提是「teacher 挑得对」，这不能只靠自证。
  用**纯方法**当独立裁判——让 teacher 翻译，再用方法算出「哪些义项确实出现在译文里」，
  看 teacher 的选择是否落在其中。方法只认译文里真实出现的字，是构造保证的硬证据。

### 候选义项的一个已知噪声

`senses.json` 直接来自上游词典，带着词典噪声，例如
`whatever → 名叫某某的东西`、`cancel → 邮票注销章/戳记`。
这些义项会稀释选择题。生产实现里建议把**人工整理的释义固定为一个候选**，
其余义项作为补充，这样「好的那一项」永远在选项里。

## 蒸馏实测结果（1500 条观察）

1500 条「词 × 句」判断：**239 秒**跑完，**0 个无效序号**，覆盖 **488 个词**。
产物 `distilled-senses.json` = 每个词的义项按真实用法频次排序。

**留一验证**（每个词留出一条观察做测试，其余用来排序；282 个词有 ≥2 条观察）：

| | 命中率 |
| --- | ---: |
| 基线：上游词典的第一个义项 | 55% |
| **蒸馏：按真实用法排序的第一个义项** | **70%（+15.6pp）** |

这是**可落地的静态产物**：一张表打进扩展，运行时不需要任何模型，
就能把「默认释义」从词典编者的顺序换成真实阅读中的使用顺序。

### 但它的上限受 teacher 自身忠实度限制

留一验证衡量的是**与 teacher 的一致**，不是正确。用**方法**当独立裁判（只认译文里真实出现的字）
复核 40 例：**teacher 与 24/34 一致 = 71%**，0 个无效输出。

不一致的 10 例是同一个模式——**teacher 挑了个语义相近、但这句译文实际没用的义项**：

| 词 | 译文 | teacher | 方法（译文里真实出现） |
| --- | --- | --- | --- |
| pretend | …教育体系**假装**它很简单 | 自诩/自称 | **伪装/假装** |
| somehow | …以某种**神奇的**方式…猜出来 | 由于某种不明原因 | **以某种方式/用某种方法** |
| audience | …迎合某个虚构的、更高级的**观众** | 读者 | **观众/听众** |
| engine | …它既是伟大作品的**引擎** | 驱动力/推动力 | **发动机/引擎** |

**所以推荐的分工是**：方法优先标注（免费、与译文严格一致、可解释），
teacher 只在方法定位不到时补位——补的那部分只有约 71% 的忠实度，应作为较低置信度处理。

## 蒸馏到小模型：LoRA 微调 0.5B

用户要的是**把 9B 的能力训练进小模型**（不是把判断存成表）。任务收窄成一个：
**只做「从词典义项里挑出符合语境的那个」，输出一个序号。**

### 数据

`make-dataset.mjs` 从真实文章抽「句子 × 多义词」样本，teacher 按**义项原序**判断
（原序对 9B 最自然，标签最干净），训练/验证时把义项**按样本 id 确定性打乱**。

为什么必须打乱：teacher 在原序下的选择分布是 **1:56% 2:29% 3:11% 4:4% 5:1%**——
位置偏好极强。不打乱的话，学生只要学会「总答第 1 个」就能拿 56%，等于什么都没学到。
打乱之后随机基线降到 **30.8%**。

实测产出：**2589 个样本**（train 2191 / valid 398），682 个词，teacher 用 laptop 的 4070
标注耗时 **410 秒**。

### 训练

```bash
HF_HOME=$PWD/.tmp-probe/hf HF_HUB_DISABLE_XET=1 HF_HUB_OFFLINE=1 \
.tmp-probe/venv/bin/python -m mlx_lm lora \
  --model mlx-community/Qwen2.5-0.5B-Instruct-4bit --train \
  --data prototype/mt-align/dataset --batch-size 4 --iters 300 --num-layers 8 \
  --learning-rate 1e-5 --mask-prompt --adapter-path prototype/mt-align/adapters \
  --steps-per-eval 150 --val-batches 5
```

- 可训练参数 **0.297%（1.466M / 494M）**，峰值显存 2.2–7.3GB，M4 上约 10 分钟（0.5 it/s）
- `HF_HUB_OFFLINE=1` 不是可选项：不设的话 `load()` 会去联网检查 HF，在这台机器上直接挂住
  （表现为「一行输出都没有」，我踩了两次）
- 验证 loss：7.37 → 0.27（iter 100 就基本收敛，300 步足够；跑 1200 步是浪费时间，试过）

### 结果

`eval_student.py`，同一批**打乱义项**的验证样本，贪心解码（`max_tokens=4`）：

| 模型 | 准确率 | 无效输出 | 延迟 |
| --- | ---: | ---: | ---: |
| 基础 Qwen2.5-0.5B | 40.7%（61/150） | 0 | 258ms |
| **+ LoRA（300 步）** | **59.3%（89/150）** | 0 | 276ms |
| 随机基线 | ~30% | — | — |

产物：`prototype/mt-align/adapters/`（LoRA 适配器，几 MB）。基础的 0.5B 本身有 40.7%
（比随机高，说明它有一点语感），微调把它拉到 59.3%。

### 必须说清的三条保留意见

1. ~~**这一轮的数据有切句 bug，而且已经修了但没重训。**~~ **已解决。** 原来的切句正则切不开
   「引号结尾」的句子（`…young men.” “In what…`），导致 294 个「句子」超过 400 字符
   （最长 2190），另有 218 个样本带 HTML 残留（Gutenberg 页码 `{307}`、`&#8217;`）。
   已修好并验证（`mt.mjs` 的 `splitSentences`），并用 v2 数据（2676 条，0 条 >400 字符、
   0 条 HTML 残留）重训。**注意重训后生成式反而降了**（51.7% → 48.8%），
   见下节「为什么应该换掉自回归小模型」——这个反常现象指向了真正的瓶颈。
2. **上限受 teacher 限制**：交叉校验显示 teacher 与「方法」的一致率只有 71%，
   学生学到的是 teacher 的判断，因此天花板在那里。
3. **59.3% 偏乐观**：验证集与训练集同分布（同一语料、同样的切句怪癖），
   且 150 条样本的 95% 置信区间约 ±8pp。真实单句输入上的绝对数字会低于此。

## 为什么应该换掉自回归小模型

0.5B + LoRA 的实测（**400 条**打乱验证样本，v2 验证集）：

| 模型 | 准确率 | 无效输出 | 延迟 |
| --- | ---: | ---: | ---: |
| 基础 Qwen2.5-0.5B | 38.5%（154/400） | 2 | 110ms |
| + LoRA（v1 数据：含长文本块） | **51.7%（207/400）** | 0 | 119ms |
| + LoRA（v2 数据：切句修好后） | 48.8%（195/400） | 0 | 134ms |
| 随机基线 | 30.8% | — | — |

两点值得记下：

- **v1（切句有 bug、句子里混着多句上下文）反而比 v2（单句）好 2.9pp。**
  差异在 ±5pp 的置信区间内，不足以定论，但它提示了一个真问题：**消歧本身需要上下文**，
  我「修好切句」把长文本块拆成单句，可能同时把有用的上下文拆掉了。
  真要验证得做「单句 vs 单句+上一句」的对照。
- 更根本的是**结构不匹配**：任务本质是「在 K 个候选里挑一个」，
  而自回归 LLM 是逐 token 生成一个数字——参数量的绝大部分用在了「会说话」上，
  而不是「会比较」。它还得额外担心非法序号。

### 换成判别式打分器（交叉编码器）

结构：小编码器 + 一个线性头，输入 `(句子+目标词, 义项)` 输出一个标量分数，
同一题的 K 个义项一起做 softmax 交叉熵；推理取 argmax。好处是结构性的：

- **永远不会输出非法序号**（不是生成，是打分取最大）
- 义项数可变、天然支持「同句多个词」（查询里写明是哪个词）
- 单次前向、无自回归 → 快一到两个数量级
- 模型小到几百 MB，**以后有机会直接跑在浏览器里**（ONNX/WebGPU），不再需要本地推理进程

脚本已写好：`prototype/mt-align/xenc/train_xenc.py`
（默认 `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`，118M 参数，多语言交叉编码器，
组内 softmax 训练，逐 epoch 报验证准确率并存最佳）。

### 成本（实测，都是这台 M4 / laptop 4070 上的真实数字）

| 阶段 | 机器 | 耗时 |
| --- | --- | ---: |
| teacher 标注 2675 题 | laptop 4070 | 412 秒（0.15 秒/题） |
| 打乱义项 + 切分 + 落盘 | — | < 1 秒 |
| 训练 1 epoch（2274 题） | Mac M4 | ~370 秒 |
| 验证 1 次（401 题） | Mac M4 | ~54 秒 |
| **单次前向（一个「句子+义项」对）** | Mac M4 | **13ms**（同题共享一次编码；首次含预热 655ms） |

折算到一篇真实文章（Paul Graham 那篇，README 基准里 410 个词需决策 × 平均 3.59 个义项）：

| 方案 | 每篇耗时 | 相对 |
| --- | ---: | ---: |
| 生成式 0.5B（逐 token 吐序号，实测 119ms/词） | 175 秒 | 基准 |
| **判别式 0.5B 打分器（13ms/义项）** | **19 秒** | **快 9.2 倍** |
| 专用小编码器（118M，保守估 6ms/义项） | 8.8 秒 | 快 20 倍 |

判别式不只是更准，还**快 9 倍**：没有自回归解码、不逐个生成 token，
而且同一题的 K 个义项**共享一次上下文编码**（只有打分头逐义项跑）。
两种方案都必须**异步渐进**（词表先标，AI 结果回来后再合入），19 秒/篇也不能阻塞渲染，
好在按句缓存后，浏览器里实际要等的只是首屏那几句。

### 产物形状的坑：别用 save_weights()

`scorer.save_weights()` 会把**整个编码器**存下来——实测产出 **994MB**，那不是适配器而是模型副本。
可训练参数只有 1.47M（0.30%），正确做法是
`mx.save_safetensors(path, dict(tree_flatten(scorer.trainable_parameters())))`（≈6MB），
加载时 `update(..., strict=False)` 做局部更新。

### 已排除：冻结特征 + 线性头（别重试）

先试过更省的做法：用本地 4bit 的 0.5B 当**冻结编码器**，取最后一个 token 的隐状态（896 维，
`xenc/features.npz` 里缓存了 9607 对），只训一个线性打分头。

| 训练方式 | 验证准确率 |
| --- | ---: |
| 裸 SGD lr=0.05（不标准化） | 45.1%，但准确率在 37%~47% 之间剧烈跳 → **假象** |
| 特征标准化 + Adam lr=0.002 | **34.7%**（几乎等于随机 30.8%） |

结论：**冻结表示里几乎不含「哪个义项合适」的信息**——光换输出结构不够，
编码器本身必须为「比较」这个目标训练过。复现命令：
`.tmp-probe/venv/bin/python prototype/mt-align/xenc/train_head.py prototype/mt-align/xenc/features.npz 150 0.002`

### 结果：LoRA + 组内 softmax 打分目标（**在 Mac 上跑的，不是 laptop**）

用 `mlx-community/Qwen2.5-0.5B-Instruct-bf16`（bf16 才能反传；4bit 会报
`QuantizedMatmul::vjp` 无梯度），只训 LoRA 与打分头（**0.30%** 可训练参数，
1.47M 个），同一题的 K 个义项一起 softmax 交叉熵。脚本 `xenc/train_scorer_lora.py`。

**跑完了，而且这是目前最好的方案。** v2 数据（2675 条），3 epoch，batch 8，lr 1e-5，
同 401 条打乱验证集：

| epoch | 验证准确率 | loss |
| ---: | ---: | ---: |
| 1 | 67.3% | 0.826 |
| 2 | 69.3% | — |
| 3 | **71.8%（288/401）** | 0.364 |

与前面所有方案的横向对比（**同一份 401 条验证集**）：

| 方案 | 准确率 | 相对随机 |
| --- | ---: | ---: |
| 随机基线 | 30.8% | — |
| 冻结特征 + 线性头 | 34.7% | +3.9pp |
| 生成式 0.5B + LoRA（LM loss） | 48.8% | +18.0pp |
| **判别式 0.5B + LoRA（组内 softmax）** | **71.8%** | **+41.0pp** |

**同样的小模型、同样的数据，只换训练目标，+23.0pp。** 这印证了前面的判断：
瓶颈不是参数量也不是数据，而是**任务结构与训练目标不匹配**——把「生成一个序号」
换成「给 K 个候选打分」，0.5B 就够了。

三个 epoch 还在单调上升（67.3 → 69.3 → 71.8），**没收敛**，加 epoch 应该还能涨。
天花板仍受 teacher 限制（teacher 与方法的一致率 71%，见前文）。

产物：`xenc/adapter.safetensors`（**5.6MB**，114 个张量 / 1.47M 参数）。
注意训练脚本里若调 `scorer.save_weights()` 会写出 994MB 的模型副本，
正确做法见上一节；跑完记得用 `xenc/shrink_adapter.py` 过滤成真适配器。

## 还没测的

- **真实文章端到端**：脚本与输入都齐了（见上节），但整篇 683 个决策点的完整运行
  被两个 MLX 进程抢内存（swap 打满 15.7G）拖住，已中止待重跑。**目前 71.8%/72.6%

  上的数还没拿到。

- **单句 vs 单句+上一句**：v1（长文本块）反而比 v2（单句）好 2.9pp，提示消歧需要上下文。

  注意：**上面那个 71.8% 是 v2「单句」版**（v2 数据没有 `context` 字段，
  `train_scorer_lora.py` 的 `build_text` 只是*支持*上下文，对 v2 等于空操作）。
- **真实浏览器里的端到端**：`npm run verify:browser` 那套 19 条断言目前**没有覆盖语境义**
  （要覆盖得在测试里起一个假打分服务，还要处理 optional permission 的授权，
  而授权在无头环境里没有用户手势可用）。所以「扩展 + 真服务」这条链只经过了

- 用更好的机翻（谷歌在可用时、或 DeepL）能否把「方法定位率」从 56% 抬高——理论上会，因为

- 一句话给多个译文（paraphrase 集成）再取并集匹配，可能抬升定位率，未测。

- **把打分器搬进浏览器**（ONNX/WebGPU）：现在必须在本机跑一个 Python 服务。
  `SensePicker` 已经是注入接口，换实现不用动流水线；但 0.5B 的转换与体积没试过。
  另外若要大批次吞吐，得先把训练改成**定宽填充**（见上文「必须逐题前向」）。

## 本地推理服务（`xenc/serve.py`）

把打分器包成 HTTP：content script 拿到句子里的生词后，把它发过来，
拿回「哪个义项最合语境」，再异步替换掉那条字典义。

```
POST /select  {"items": [{"id": "s1", "sentence": "…the engine and the rudder of great work.", "word": "engine"}]}
           →  {"results": [{"id": "s1", "index": 4, "selected": "驱动力/推动力", "scores": [...], "ms": 41.2}]}
GET  /health  →  {"ok": true, "adapter": "…", "multiSenseWords": 2413, "maxItems": 2048}
```

两个设计决定，都是踩过才知道的：

1. **义项表放在服务端，不放进扩展。** `senses.json` 有 229K，而现有词典数据才 192K——
   打进 content script 等于让每个页面都多下一份，很不划算。服务端持有义项表之后，
   扩展只发 `句子 + 单词`，新增字节为 0；而且义项表可以随时迭代，不用重新发版。
   请求里仍可显式带 `senses` 覆盖（调试用）。词不在表里或只有 1 个义项时返回
   `index: -1` + `reason`，调用方**保持原释义不动**——这不是错误，是常态。
2. **必须逐题前向，不能跨题乱批。** 这是本轮最容易踩的坑：
   训练时（`train_scorer_lora.py` 的 `encode_batch`）每题填充到**本题**最长的那条，
   然后取**最后一个位置**的隐状态。短序列读出的其实是填充位——一个被训练固定下来的池化约定。
   一旦把不同题目的义项混进同一个矩形批次，全部序列被填充到「整批最长」，
   短题的读出位置就平移了,与训练分布不一致,**71.8% 不再复现**。
   所以服务是「一题一次前向」（K 个义项共享一次上下文编码）。
   想要真正的大批次吞吐，得先重训成定宽填充（或左填充取末位真实 token）。

起服务与自检：

```bash
export HF_HOME=$PWD/.tmp-probe/hf HF_HUB_DISABLE_XET=1 HF_HUB_OFFLINE=1
.tmp-probe/venv/bin/python prototype/mt-align/xenc/serve.py --self-test        # 不起 HTTP，跑内置样例
.tmp-probe/venv/bin/python prototype/mt-align/xenc/serve.py --port=8317       # 起服务
curl -s localhost:8317/health
```

**已验证**（真起服务、真发请求，不是只看代码）：

```
GET /health → {"ok":true, ..., "multiSenseWords":2413, "maxItems":2048}

POST /select  三条一次发过去（senses 省略，走服务端义项表）
  s1  "…both the engine and the rudder of great work."  → 驱动力/推动力   (index 4, 295ms)
  s2  "The car engine needs repair."                    → 发动机/引擎     (index 0, 126ms)
  s3  词不在义项表里                                      → index -1, reason "unlisted"
```

**s1 与 s2 是同一个词、不同句子，选出了不同的义项**——这是整条链上最有说服力的一条证据：
模型确实在读句子，而不是背「engine 的常用义」。也正是扩展里「按处更新」而非「按词元更新」
的依据（同一个词在一个页面里可能有两处、两个义项）。

## 真实文章端到端（`xenc/pick-candidates.mjs` + `xenc/annotate-article.py`）

前面所有准确率都是**同分布留出集**上的。真实文章上要另跑一遍，因为：
候选词来自生产同一套切句与取词逻辑，义项数分布也不同（实测平均 **4.67** 个，
比留出集的 3.59 更多）。

```bash
node prototype/mt-align/xenc/pick-candidates.mjs \
  --article=.tmp-articles/https_paulgraham_com_greatwork_html.html
.tmp-probe/venv/bin/python prototype/mt-align/xenc/annotate-article.py \
  --out=prototype/mt-align/xenc/annotated-greatwork.md
```

切句**故意放在 Node 侧**（复用 `mt.mjs` 的 `splitSentences`/`candidateWords`），
打分放在 MLX 侧，中间用一份 JSON 交接——目的是不让 Python 里重写一遍切句逻辑，
否则「生产用的切句」与「评测用的切句」会悄悄分叉，测出来的数就不是线上的数。

## ⚠️ 跑间方差约 1.5pp：小差异不要当结论

同数据、同超参（v2，8 层 LoRA，lr 1e-5）跑两次，逐 epoch 验证准确率：

| epoch | 第一次（3 epoch 那次） | 第二次（8 epoch 那次） |
| ---: | ---: | ---: |
| 1 | 67.3% | 69.1% |
| 2 | 69.3% | 70.3% |
| 3 | 71.8% | 72.6% |

**同一配置的 run-to-run 差异就有 ~1pp，而且是整体平移。**
后果：**任何小于 2pp 的对照差异都不能当结论**（v1 vs v2 那个 2.9pp 差异本来就
在置信区间内，现在更不该当证据）。要做对照就得同种子多次取平均，或者用远大于噪声的效应
——判别式 vs 生成式那 23pp 就完全不受影响。

## 接进扩展（已完成的部分）

打分器已经接进生产扩展，**默认关闭**，走的是与在线词典相同的「内容脚本 → service worker → 外部服务」链路。

| 关注点 | 做法 |
| --- | --- |
| 义项表在哪 | **在服务端**。`senses.json` 229K，打进 content script 等于每页多下一份（现有词典才 192K）。扩展只发 `句子 + 单词`，义项表可随时迭代不用发版 |
| 请求从哪发 | **service worker**（`src/background/sense.ts`）。内容脚本直接 fetch 受页面 CSP/CORS 约束，还会把本机地址暴露在页面上下文里 |
| 权限 | `optional_host_permissions` 里的 `http://127.0.0.1/*`、`http://localhost/*`，在设置页点「授予权限」时申请；不明文允许任意 http 主机 |
| 怎么找句子 | `src/content/sentence-context.ts`：最近的**块级祖先**的文本 + 词在段内的偏移 → 保留偏移的切句（`src/core/sentence.ts`） |
| 中文释义会不会污染上下文 | **会**，所以流水线改成**三阶段**：先算句子与匹配 → 渲染词典义 → 异步回填语境义。第一段必须在任何渲染之前算完，否则拿到的是 `ubiquitous（无处不在的）` |
| 阻塞 | **不阻塞**。`processNodes` 不 await 打分；模型再慢，正文也已经用词典义渲染完了 |
| 失败 | 服务没起 / 超时 / 返回垃圾 → 静默保持词典义。`pick()` 在设计上**永不抛错**，这不是错误路径而是常态 |
| 逐处而非按词 | 同一个词在两处可能是两个义项，所以渲染器按**每次渲染**分配 id（`data-wordmark-gloss-id`），不能用 lemma 当更新键 |

新增（均在 `src/`，已过 `npm run check`：223 测试 / typecheck / lint / 构建校验 / 两个冒烟）：

- `core/sentence.ts`、`content/sentence-context.ts` — 保留偏移的切句 + DOM 里定位句子
- `core/sense-selector.ts` — 缓存、批、绝不抛错的客户端（`SensePicker` 是注入接口，便于换 ONNX/WebGPU）
- `background/sense.ts` — service worker 侧转发
- `content/gloss-renderer.ts` — 新增 `onGloss` 回调与 `updateGlossText(id, gloss)`（按处更新，只改释义节点文本）
- 设置页新增「语境义挑选（可选 · 本机模型）」一节

### 集成时抓到的两个真 bug

1. **设置页会直接崩。** `read: (s) => s.sense.enabled` 假定字段一定存在；
   而设置页拿到状态后**没有过 `sanitizeSettings`**，喂进来一个旧形状的对象
   （UI 冒烟测试就是这种来源）就抛 `TypeError: Cannot read properties of undefined`。
   修法是所有入口统一走 `adoptSettings()` 收敛一次。**这类 bug 单测抓不到，是既有的
   真浏览器/UI 冒烟测试抓到的**——再次说明那套冒烟不是装饰。
2. **渲染会污染后续的上下文。** 一开始按「边渲染边算句子」写，标注过的词会把中文释义
   留在段文本里，后面所有词的上下文都变成 `ubiquitous（无处不在的）`。
   改成三阶段（先算完再渲染）并在拼接时排除释义节点。
   测试 `sentence-context.test.ts` 里有一条专门钉这个行为。
