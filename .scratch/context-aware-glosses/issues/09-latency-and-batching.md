## Question

逐句请求的延迟与批处理预算怎么定？

已知（01 的事实票）：llama.cpp 的 `/completion` 接受 prompt 数组、一次可多句；MLX `mlx_lm.server`
一次只收一个 prompt、批处理靠并发。实测 9B：laptop 首 308ms / 命中提示缓存 97ms，一次 6 句约 0.75 秒/句；
M4 首 9166ms / 后续 809ms。一页正文可能数百句，其中含生词的句子只占少数。

要定：

- **只处理含生词的句子**的筛选门槛（按当前生词线）——这决定请求量级。
- **批量与并发**：一次打包几句？端点是 MLX 那种单 prompt 时并发度多少？
- **缓存**：句级缓存的键（句子 hash？带不带词形）与存放（`chrome.storage.local` 的 LRU、容量上限）、
  是否跨页面与跨标签共享。
- **交互时序**：译文异步到达——先标 `senses[0]` 再原地升级为语境义，还是等译文到达才标（页面可能空白很久）？
  这条与 05（置信度与 UI）耦合，需一起定。
- **预算**：单页请求上限、超时阈值、超时后的回退（承接 03 的「静默回退」）。

闭票时给出：请求量级估算 + 批量/并发参数 + 缓存设计 + 交互时序。

## Answer

用户委托我决策。先说一条**实现缺陷**，它决定预算怎么定。

**缺陷：把「失败」和「没得选」缓存成了同一件事。**
`SenseSelector.pick`（`src/core/sense-selector.ts:131-133`）在这一批请求返回后，对每个 pending 项写入
`fetched.get(id) ?? NO_PICK`；而 `#fetchPicks` 在超时 / 连不上 / 非 2xx 时返回空 Map。于是
**一次超时会把整批（最多 `maxPerPage` 条）永久缓存成「没得选」**，这些词在本页再也不重试。

**预算算术**：服务端逐题前向、且有全局锁（mlx 图执行非线程安全），13ms/义项；真实文章平均 **4.67** 个义项/题
→ 约 **61ms/题**。`maxPerPage` 默认 300 → 单次请求约 **18 秒**，而 `timeoutMs` 默认 **8000ms**。
**长页面上默认配置必然超时**，而按上面的缺陷，超时后这 300 处会被整体标成「没得选」。

**决定**：

1. **区分两种否定**：只有服务端明确给出 `index: -1`（`unlisted` / `single-sense`）才落否定缓存；
   超时、连不上、非 2xx、响应格式不对——**一律不缓存**，留给重扫 / 滚动时重试。
2. **分片批处理**：不把 `maxPerPage` 一次发出去，切成小批顺序发（默认 **32 题/批**，约 2 秒），
   每批独立超时、独立缓存；一批失败不牵连其他批。服务端有全局锁，**并发无意义**，顺序发即可。
3. **超时阈值**：单批超时默认 **3000ms**（32 题约 2s，留 50% 余量），不再用 8000；设置页范围不变。
4. **页面预算**：`maxPerPage` 语义明确为「本页最多挑多少处」，保持 300；候选按**阅读（DOM）顺序**取，
   先到先得，不引入「可见区优先」。
5. **不做自动重试**：页面级增强，失败就是这次没有；但因为不再缓存失败，滚动 / 重扫会自然重试。
6. **交互时序确认**：先标词典义、拿到结果**按处替换**（已实现），不阻塞渲染。
7. **不为大批次吞吐去重训定宽填充**：本次不需要——分片已让超时可控，重训的收益是吞吐，
   单页几百处的场景下分片足够。→ 移出范围。
