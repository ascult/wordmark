## Question

运行态用哪条链路、哪个 provider，把「这句里的那个义项」判出来？

要定：

- **链路**：方法定位（把词典义往整句译文里定位，定位到的片段即语境义）为主、
  LLM「义项选择题」补位？还是纯 LLM 挑义项？还是只做方法、定位不到就回退现状？
  原型的实测：方法定位率 28%（原样）→ 56%（让模型列候选说法后用方法定位），
  小模型选择题 1.5B 有效作答 100% 但与译文相容仅 38%；teacher 与方法一致率仅 71%。
- **provider**：公网在线接口，还是**只允许本地/局域网端点**（与 Q3=b 的「默认开但只允许本地网络」一致）？
- **回退**：endpoint 不可达 / 超时 / 未授权时，退回现状（本地首义项）还是干脆不标？

闭票时给出：一条确定的运行态链路 + provider + 回退策略，以及它与 01 号事实票结论的对应关系。

## Answer

用户委托我决策，依据 01 的事实票。

**1) Provider = 本机/局域网的 OpenAI 兼容端点**（用户可配 URL，如 `http://127.0.0.1:8080` 或经隧道/局域网的
laptop 端点）。公网服务不作默认路径——与「默认开但只允许本地网络」直接冲突，且 MyMemory 匿名配额仅
5,000 字符/天（约几十句）、ToS 禁止一次超过一段、提交内容长期留存并共享第三方。是否保留公网整句兜底 →
已移出范围（见 map 的 Out of scope）。现有针对**单词**的 MyMemory 兜底保持原样、不动。

**2) 链路 = 方法优先 + 端点补位**：
1. 只对**含生词的句子**向端点请求**整句译文**（不要求端点给对齐——01 已证没人给子句对齐，方法在本地做定位）；
2. 本地把该词的候选义项（`senses`）往译文里定位，命中即得语境义（与译文严格一致、可解释、零额外调用）；
3. 定位不到时，把候选义项列表交给端点做**义项选择题**，只让它输出序号；
4. 仍失败 → 回退。

**3) 不改造现有 `{word}` 契约去承载整句**（它的查询正则、单标量点路径、24 字中文清洗逐条都不适配句子）。
**新增一条独立的「整句翻译」通路**（新消息类型 + 新 provider kind），与词级 provider 并存。改动面见 01。

**4) 回退**：端点未配置 / 不可达 / 超时 / 未授权 → **静默退回现状**（`senses[0]`，即人工 `gloss`），
不标错、不打断阅读。

**5) 「默认开」落地**：一旦配置了端点即默认启用，不需额外开关；没配端点时行为与现状完全一致，且**公网域名一律不发**。

**6) 批量与缓存**：句级缓存（句子 hash → 译文）+ 一次打包多句（llama.cpp 支持 prompt 数组；MLX 只能并发）。
具体参数与预算 → 新开票 09（延迟与批处理）。
